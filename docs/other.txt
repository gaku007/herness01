**ハーネスエンジニアリング（Harness Engineering）**とは、
「AIエージェントが正しく動く環境（ハーネス）を設計すること」
で、エンジニアはコードを書くより AIが間違えない仕組み・環境を作ることに集中するという開発方法です。
OpenAIの実験では
3人のエンジニア＋AIエージェントで100万行のコードを生成しましたが、その鍵がこの「ハーネス」です。

（現実の開発での設定手順）

この順番が一番再現性が高いです。

手順2：AGENTS.md を作る
ここが中核です。
AIに対する“現場ルール”を明文化します。
最初はこれで十分です。

# AGENTS.md

## Goal
このリポジトリは、FastAPIベースのAPIを開発するためのもの。

## Allowed changes
- `src/`, `tests/`, `docs/` のみ編集可
- 依存追加が必要なら理由をPR本文に記載
- 秘密情報や認証情報は絶対にコミットしない

## Coding rules
- Python 3.12
- Ruffでlint
- pytestでテスト
- 型ヒント必須
- 1機能追加ごとに最低1テスト追加

## Workflow
1. Issueを読む
2. 専用branchを切る
3. 実装前に変更方針を `docs/plan.md` に短く書く
4. 実装
5. テスト実行
6. 失敗したら修正
7. PRを作成

## Constraints
- 既存の公開APIを壊さない
- 大規模リファクタは別Issueに分離
- 1PR 1目的を守る

## Done definition
- テスト通過
- lint通過
- 型チェック通過
- 変更理由が説明できる
ポイントは、
「何をしてよいか」より「何をしてはいけないか」を書くこと です。
OpenAIのCodexループは、モデルがツール呼び出しを繰り返しながらローカル環境を書き換え得る前提なので、境界条件を明示すること が実運用ではかなり大事です。 

手順3：AIが呼ぶコマンドを scripts/ に統一する
AIに毎回長いコマンドを考えさせない方が安定します。
「入口」を固定します。
touch scripts/setup.sh scripts/lint.sh scripts/test.sh scripts/typecheck.sh
chmod +x scripts/*.sh
中身の例です。
scripts/setup.sh

#!/usr/bin/env bash
set -euo pipefail
python -m venv .venv
source .venv/bin/activate
pip install -U pip
pip install -r requirements.txt
scripts/lint.sh
#!/usr/bin/env bash
set -euo pipefail
ruff check .
ruff format --check .
scripts/test.sh
#!/usr/bin/env bash
set -euo pipefail
pytest -q
scripts/typecheck.sh
#!/usr/bin/env bash
set -euo pipefail
mypy src
AIには
「品質確認は必ず scripts/lint.sh scripts/test.sh scripts/typecheck.sh を使う」
と教えます。
これがハーネスです。
つまり、AIの自由度を減らして、正しい軌道に乗りやすくするわけです。

手順4：CIを必須化する
ローカルでたまたま通った、を防ぎます。
GitHub Actionsならまずこれで十分です。
.github/workflows/ci.yml

name: ci

on:
  pull_request:
  push:
    branches: [main]

jobs:
  quality:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install
        run: |
          pip install -U pip
          pip install -r requirements.txt

      - name: Lint
        run: bash scripts/lint.sh

      - name: Type check
        run: bash scripts/typecheck.sh

      - name: Test
        run: bash scripts/test.sh
ここで大事なのは、
AIが書いたコードを人が読む前に機械が落とす ことです。
OpenAIの記事でも、重要なのはエージェントを支える フィードバックループ と 制御システム の設計だとされています。CIはその中心です。 

手順5：ブランチ保護を入れる
GitHub側で次を設定します。
main への直接push禁止
PR必須
CI成功必須
squash merge推奨
可能ならレビュー1件必須
これでAIが暴走しても、本線は守れます。
ハーネスエンジニアリングは「AIを信用する」のではなく、
信用しなくても壊れにくい仕組みを先に作る ことです。

手順7：計画ファイルを1枚置く
AIは途中で目的を見失いやすいので、短い作業計画を残させます。
docs/plan.md

# Current task plan

## Goal
ユーザー登録APIにメール形式バリデーションを追加する

## Files to change
- src/api/users.py
- tests/test_users.py

## Risks
- 既存レスポンス形式を変えない
- 既存テストを壊さない
これは地味ですが効きます。
コンテキストが長くなるとエージェントは履歴やツール出力を大量に抱えるので、短い再同期ポイント があるとかなり安定します。OpenAIもコンテキストウィンドウ管理をエージェントの重要な責務として説明しています。 
手順8：AIの権限を分ける

レベル3

危険操作は 人の確認必須 にします。

OpenAIの記事では、エージェントはツール経由でローカル環境を変更し得るので、出力は文章だけではありません。だからこそ、どこまで変更してよいかの制御 が肝です。

ハーネスを英語で　手短に

Harness（ハーネス）
手短に言うと：

制御・補助のための仕組みや枠組み
元々の意味
馬具（馬を制御する装具）
そこから派生して
機械やソフトウェアを安全に動かすための制御環境
ソフトウェアでの意味
システムやAIを安全に動かすための実行環境・制御フレームワーク
例
test harness（テスト用実行環境）
safety harness（安全制御）
AI harness（AI制御環境）
一言で言うなら
Harness = 制御用の枠組み 🧠




=============
AI開発（ハーネス）でのおすすめ設定
これが鉄板です。
✔ Require pull request
✔ Require status checks
✔ Require branches up to date
✔ Require review (1人)
✔ Block force push
✔ Block deletion
これで
AI → PR作成
CI → テスト
人 → merge
の 安全ループ ができます。
